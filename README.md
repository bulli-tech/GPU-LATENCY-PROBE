# GPU-CHECKUP

Быстрая диагностика одной из самых коварных проблем GPU-сервера: **деградации
канала до GSP** — встроенного процессора, который управляет картой.

Проблема выглядит так: `nvidia-smi` показывает нормальную температуру, питание и
загрузку, ошибок в логах нет, но обучение и инференс замедляются в разы. Виноват
при этом не код, не фреймворк и не версия драйвера, а карта.

`GSP-CHECKUP.py` находит это за один запуск и говорит прямо: какая карта больна,
какая здорова.

## С чем мы столкнулись

Сервер 8×A100-SXM4-40GB, модели на vLLM работали в 100 раз медленнее ожидаемого:
1.9 tok/s вместо 200+. Профилировщик показывал паузы в секунды на рангах 1 и 2,
пока ранги 0 и 3 работали нормально. При этом выглядело это как «NCCL ждёт»,
«медленный host callback», «проблема аллокатора».

Что проверялось и не помогло:

- переписывание offload-ядер (нашли и исправили реальные баги, но скорость не та);
- отключение фоновых потоков аллокатора;
- изолированные тесты NCCL — маленький AllGather занимает 55 мкс, всё в норме;
- изолированные host callback — доли миллисекунды;
- смена драйвера 610.57.04 → 580.196.07 (CUDA 13.3 → 13.0) — ни одна цифра не изменилась.

Что оказалось причиной: **сервер собран из двух партий карт**. Три карты одной
ревизии работали нормально, пять других — нет.

| Карты | Board Part Number | VBIOS | Статус |
|---|---|---|---|
| 0, 3, 7 | 692-2G506-0200-**002** | 92.00.**36**.00.04 | здоровы |
| 1, 2, 4, 5, 6 | 692-2G506-0200-**000** | 92.00.**0C**.00.05 | больны |

Совпадение 8 из 8, без исключений. На больных картах каждый вызов CUDA API стоит
~160 мкс вместо ~2 мкс, а под нагрузкой уходит в секунды. В логах ядра при этом
можно поймать `Xid 119` — таймаут ожидания ответа от GSP.

## Как это выявлять

### Механизм

Драйвер общается с GSP по RPC. У здоровой карты ответ приходит за микросекунды.
У больной каждый запрос обслуживается в сотни раз дольше, а при нескольких
потоках запросы выстраиваются в очередь — и время уходит в секунды.

Проверять надо именно **стоимость вызова CUDA API на уже завершённой работе**.
Если событие завершено, вызов ничего не ждёт на GPU — значит всё время сверх
нормы это и есть стоимость канала до GSP.

### Ключевые признаки

1. **Задержка бинарная**: либо единицы микросекунд, либо сотни. Промежуточных
   значений почти не бывает. Это самый сильный признак.
2. **Не зависит от версии драйвера.** Переустановка не помогает — проверено.
3. **`nvidia-smi` ничего не показывает.** Температура, питание, загрузка в норме.
4. **Проявляется под нагрузкой.** В простое карта может отвечать быстро, но при
   нескольких потоках деградация видна сразу.
5. **Сравнение ревизий решает.** Если у части карт другой `Board Part Number`
   или `VBIOS`, и они группируются по поведению — причина найдена.

### Что смотреть, если скрипт показал BAD

```bash
# сравнить ревизии всех карт
for i in 0 1 2 3 4 5 6 7; do
  echo "=== GPU$i ==="
  nvidia-smi -i $i -q | grep -E "Serial Number|VBIOS Version|Board Part Number"
done

# посмотреть, не было ли таймаутов GSP в логах ядра
sudo dmesg -T | grep -E "Xid|GSP" | tail -20
```

Что означают findings:

- **разные `VBIOS Version` у здоровых и больных** — две партии; обновляйте VBIOS
  на отстающих или исключайте их из работы;
- **`Xid 119` в dmesg** — драйвер не дождался ответа от GSP; это следствие той же
  деградации, а не отдельная авария;
- **одинаковые ревизии, но разное поведение** — тогда смотрите питание и
  охлаждение конкретного слота, это уже другая история.

## Запуск

Скрипт самодостаточный: только Python 3.8+ и `libcudart`, которая уже стоит
вместе с драйвером NVIDIA. Никаких весов, моделей и скачиваний.

```bash
python3 GSP-CHECKUP.py            # если карт несколько — предложит выбор
python3 GSP-CHECKUP.py --all      # все карты
python3 GSP-CHECKUP.py --list     # только перечислить карты
python3 GSP-CHECKUP.py -d 0 -d 3  # конкретные карты
python3 GSP-CHECKUP.py --threads 8  # больше потоков в нагрузке
```

Если в системе чего-то не хватает, скрипт не падает с невнятной ошибкой, а прямо
говорит, чего именно нет:

```
НЕ МОЖНО ЗАПУСТИТЬ: не хватает компонентов

  • не найдена библиотека libcudart
  Linux: она лежит рядом с драйвером или в CUDA toolkit
    проверьте: ls /usr/local/cuda/lib64/libcudart.so*
```

### Что вы получите

```
Проверяю карт: 8  (потоков в нагрузке: 4)
Задержка — медиана одного вызова cudaEventQuery, микросекунды.

  # модель                           cold     warm     loaded  вердикт
------------------------------------------------------------------------------
  0 NVIDIA A100-SXM4-40GB             2.5      2.2       22.8  OK
  1 NVIDIA A100-SXM4-40GB             2.4      2.1      156.9  BAD
  ...
------------------------------------------------------------------------------

Здоровы (3): GPU 0, GPU 3, GPU 7
С деградацией GSP (5): GPU 1, GPU 2, GPU 4, GPU 5, GPU 6
```

Колонки:

- **cold** — сразу после создания контекста, до первой работы. У некоторых
  здоровых карт тут бывает 150–200 мкс — это холодный старт, а не болезнь.
- **warm** — после первой реальной операции. Самая честная характеристика.
- **loaded** — под нагрузкой в несколько потоков. Именно здесь деградация
  обостряется до секунд.

Код возврата: `0` — всё здорово, `1` — найдены проблемы, `2` — не удалось
запуститься (нет CUDA, нет карт).

## Внутри контейнера

Если GPU доступны только внутри контейнера, смонтируйте скрипт и запустите:

```bash
docker run --rm --gpus all -v "$PWD/GSP-CHECKUP.py:/tmp/g.py:ro" \
  <образ с python и cudart> -I /tmp/g.py --all
```

Важно: `--gpus device=N` меняет индексацию — карта получит индекс 0 внутри
контейнера. Используйте `--gpus all`, чтобы индексы совпадали с хостовыми.

## Ограничения

- Скрипт измеряет симптом, а не причину. Вердикт `BAD` означает «канал до GSP
  деградировал», но почему — решают сравнение ревизий, логи ядра и вендор.
- Пороги (`HEALTHY_US = 30`, `BAD_US = 100`) подобраны по A100. Для других
  архитектур прогоните скрипт на заведомо исправной карте и посмотрите `warm`.
- Если карта занята чужой задачей, `loaded` будет завышен. Проверяйте на простое.
- GPU в режиме `EXCLUSIVE_PROCESS` может не дать открыть второй контекст — скрипт
  сообщит об ошибке, это нормально.
